# dev-kit v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `dev-kit` package, installable from a private registry or over git, that the three
projects on this machine can each take conventions and tooling configuration from, one module
at a time.

**Architecture:** No source code and no build step — the package is data: JSON configuration,
markdown rules, and one shell library. Because there is nothing to compile, the test suite is a
**consumer fixture**: a throwaway project under `tests/fixture/` that installs the kit by
relative path and proves each module does what it claims. `./check` runs every `checks/*.sh` in
order and is the only verification command.

**Tech Stack:** Node 24+, npm, TypeScript 7 (as a consumer, never a dependency), Prettier,
bash. The package itself has **no dependencies and no devDependencies it ships** — a shared set
of conventions must not drag a tree into every project that adopts it.

**Spec:** [docs/superpowers/specs/2026-09-08-dev-kit-design.md](../specs/2026-09-08-dev-kit-design.md)
— read §3 (shape), §4 (the consumption contract) and §5 (the extraction boundary) before
starting. §5 is the one that matters most: the rules are **extracted**, not copied.

---

## Global Constraints

Every task's requirements implicitly include this section.

**Commits.** Conventional Commits, `type(scope): subject`, imperative mood, lowercase, ≤72
characters. **The subject line is the whole message: no body, no footers, no `Co-Authored-By`
trailer.** This is the rule this repository exists to hold (spec §5), so the repository that
holds it complies from its first commit.

**English everywhere:** code, identifiers, comments, documentation, commit messages.

**Names.** Throughout this plan, **the older project** and **the newer project** are the two
applications already running, and **the unbuilt project** is the third, designed but not yet
written. Refer to them by role in prose. A literal path appears only inside a command block
that has to run — there is exactly one, in Task 5 Step 5 — and `rules/writing.md`, built in
Task 4, is the rule this follows.

**No dependencies.** `package.json` has no `dependencies` and no `peerDependencies`. Consumers
install this to *stop* inheriting things they did not ask for.

**No build step.** No `prepare`, no `prepublishOnly`, nothing that compiles. A git dependency
that has to build is a git dependency that breaks on a machine missing a toolchain.

**Every module is independently optional** (spec §4). No module may require another. A project
taking only `rules/commits.md` is using the kit correctly, and nothing may warn it otherwise.

**Package name:** `dev-kit`, unscoped. **Repository:** `github:AlexeyVanyukevich/dev-kit`.

The name is deliberate and the spec's 2026-09-23 amendment (§4) argues it in full. Two
consequences bind this plan. The name is **taken on the public registry** by an unrelated
abandoned package, so nothing here may ever run a bare `npm publish` without a registry
explicitly configured — publishing is always to the private registry, never the default one.
And because an unscoped name cannot be routed by scope, a consumer of the registry channel
sets `registry=` for the whole project rather than one `@scope:registry=` line.

Neither affects how this plan is verified: every check installs the fixture by relative path
(`file:../..`), which touches no registry at all.

**Nothing here modifies the three consuming projects.** This plan builds the kit and proves it
against a fixture. Migrating any consumer is separate work, per spec §8.

**Before every commit:** `./check` from the repository root.

```
  http.md              error shape, additionalProperties, framework 4xx translation
  layout.md            modules/<entity>/ with four files; shared/ and db/
  testing.md           tests first; real Postgres; derived facts

  writing.md           refer to projects by role, not by name

  node.json            extends base — NodeNext, types: node
  web.json             extends base — bundler, DOM, jsx, verbatimModuleSyntax

ignore/
  gitignore            the common core; a project appends its own
  prettierignore       the common core; a project appends its own
```

**Why `checks/` and not a test framework.** Adding Vitest to verify JSON files would give the
package a devDependency, a lockfile and a `node_modules` of its own, to assert things that are
better asserted by running the actual tools a consumer runs. `tsc` is the test for
`tsconfig/`; `prettier --check` is the test for `prettier/`. The suite drives the real tools
against a real consumer, which is the only thing that proves the contract holds.

### Task 1: The package, and the harness that proves it

**Files:**
- Create: `package.json`, `.gitignore`, `check`, `checks/10-package.sh`
- Create: `tests/fixture/package.json`

**Interfaces:**
- Consumes: nothing.
- Produces:
  - The package identity every later task extends: name `dev-kit`, and an
    `exports` map whose entries later tasks add to.
  - `./check` — runs each `checks/*.sh` in filename order, aborts on the first failure,
    prints a green summary. Every later task adds one file to `checks/`.
  - `tests/fixture/` — a consumer project depending on `"dev-kit": "file:../.."`.
    Tasks 2, 3 and 4 add files to it.

- [ ] **Step 1: Write the failing check**

`checks/10-package.sh`:

```bash
#!/usr/bin/env bash
# The package resolves from a consumer and ships exactly what it means to ship.
set -euo pipefail

fixture="tests/fixture"

# `npm pack` is the only honest answer to "what does a consumer get?" — `files` and
# `.npmignore` interact in ways that are easier to check than to reason about.
packed="$(npm pack --dry-run --json 2>/dev/null | node -e '
  const [pkg] = JSON.parse(require("fs").readFileSync(0, "utf8"))
  console.log(pkg.files.map((f) => f.path).sort().join("\n"))
')"

expect_packed() {
  grep -qx "$1" <<< "$packed" || { echo "  ✗ $1 is not in the package"; return 1; }
}

expect_packed 'package.json'

# A consumer must be able to resolve the package by name. This is what every later module
# rides on, so it is checked once here rather than in each of them.
( cd "$fixture" && npm install --silent --no-audit --no-fund )
resolved="$( cd "$fixture" && node -e '
  console.log(require.resolve("dev-kit/package.json"))
')"
[ -f "$resolved" ] || { echo "  ✗ the package does not resolve from the fixture"; exit 1; }

name="$(node -p "require('$resolved').name")"
[ "$name" = "dev-kit" ] || { echo "  ✗ resolved the wrong package: $name"; exit 1; }

# The kit exists so consumers stop inheriting things. It may never bring a tree with it.
for field in dependencies peerDependencies; do
  count="$(node -p "Object.keys(require('$resolved').$field ?? {}).length")"
  [ "$count" = 0 ] || { echo "  ✗ package.json declares $field"; exit 1; }
done

# A git dependency that has to build breaks on a machine missing a toolchain.
for script in prepare prepublishOnly install postinstall; do
  has="$(node -p "Boolean(require('$resolved').scripts?.$script)")"
  [ "$has" = false ] || { echo "  ✗ package.json declares a $script script"; exit 1; }
done

echo "  ✓ package resolves, ships package.json, brings no dependencies and builds nothing"
```

- [ ] **Step 2: Write `check`**

```bash
#!/usr/bin/env bash
#
# The whole verification suite. Each checks/*.sh proves one module's contract by running the
# tool a consumer would run, against tests/fixture.
#
set -euo pipefail
cd "$(dirname "${BASH_SOURCE[0]}")"

if [ -t 1 ]; then
  BOLD=$'\033[1m'; RED=$'\033[31m'; GREEN=$'\033[32m'; OFF=$'\033[0m'
else
  BOLD=''; RED=''; GREEN=''; OFF=''
fi

only="${1:-}"
ran=0

for script in checks/*.sh; do
  [ -e "$script" ] || continue
  name="$(basename "$script" .sh)"
  if [ -n "$only" ] && [[ "$name" != *"$only"* ]]; then continue; fi

  printf '%s→ %s%s\n' "$BOLD" "$name" "$OFF"
  if ! bash "$script"; then
    printf '%s✗ %s failed%s\n' "$RED" "$name" "$OFF" >&2
    exit 1
  fi
  ran=$((ran + 1))
done

if [ "$ran" = 0 ]; then
  printf '%s✗ no checks matched%s\n' "$RED" "$OFF" >&2
  exit 1
fi

printf '%s✓ %d checks passed%s\n' "$GREEN" "$ran" "$OFF"
```

Then: `chmod +x check`

### Task 2: The TypeScript bases

Three files. `base.json` carries the strictness and is extended by the other two, so a project
picks a runtime rather than restating compiler flags.

**Files:**
- Create: `tsconfig/base.json`, `tsconfig/node.json`, `tsconfig/web.json`
- Create: `checks/20-tsconfig.sh`
- Create: `tests/fixture/tsconfig.json`, `tsconfig.probe.json`, `tsconfig.web.json`
- Create: `tests/fixture/src/clean.ts`, `src/violations.ts`, `src/dom.ts`
- Modify: `package.json` — three `exports` entries
- Modify: `tests/fixture/package.json` — add `typescript` to `devDependencies`

**Interfaces:**
- Consumes: the package identity and `./check` (Task 1).
- Produces three specifiers a consuming project extends:
  - `dev-kit/tsconfig/base` — `strict`, `noUncheckedIndexedAccess`,
    `exactOptionalPropertyTypes`, `target: ES2023`, `skipLibCheck`
  - `dev-kit/tsconfig/node` — base plus `module`/`moduleResolution: NodeNext`,
    `types: ["node"]`
  - `dev-kit/tsconfig/web` — base plus `ESNext`, `moduleResolution: bundler`,
    `lib: ["ES2023", "DOM", "DOM.Iterable"]`, `jsx: react-jsx`, `noEmit`,
    `verbatimModuleSyntax`

  None of the three sets `outDir`, `rootDir`, `include` or `types: ["vite/client"]`. Those are
  answers about one project's directory layout, and a shared base that guesses them is a base
  every project has to override.

- [ ] **Step 1: Write the fixture sources**

`tests/fixture/src/clean.ts` — must compile under `node`:

```ts
export interface Booking {
  id: string
  note?: string
}

export function firstId(bookings: readonly Booking[]): string | undefined {
  // Correct under noUncheckedIndexedAccess: the index may be out of range, and the type says so.
  return bookings[0]?.id
}

export function withNote(booking: Booking, note: string | undefined): Booking {
  // Correct under exactOptionalPropertyTypes: the key is omitted rather than set to undefined.
  return note === undefined ? { id: booking.id } : { id: booking.id, note }
}
```

- [ ] **Step 3: Write the failing check**

`checks/20-tsconfig.sh`:

```bash
#!/usr/bin/env bash
# The bases are extendable by specifier, and the strictness they promise actually bites.
set -euo pipefail

cd tests/fixture
npm install --silent --no-audit --no-fund

# 1. The clean sources compile. This is what proves `extends` resolved at all: an unresolved
#    extends is a hard tsc error, not a silent fallback to defaults.
npx tsc --noEmit -p tsconfig.json ||
  { echo "  ✗ clean.ts did not compile under tsconfig/node"; exit 1; }

# 2. The violations do not. Asserting on codes rather than on prose keeps this working when
#    the compiler rewords a message.
probe="$(npx tsc --noEmit -p tsconfig.probe.json 2>&1 || true)"

for code in TS2322 TS2375; do
  grep -q "$code" <<< "$probe" || {
    echo "  ✗ expected $code from violations.ts; strictness is not being inherited"
    echo "$probe"
    exit 1
  }
done

# 3. The web base carries the DOM lib. Under tsconfig/node this file must NOT compile, which
#    is what stops a Node project silently believing it has a `document`.
npx tsc --noEmit -p tsconfig.web.json ||
  { echo "  ✗ dom.ts did not compile under tsconfig/web"; exit 1; }

npx tsc --noEmit --strict --types node --lib ES2023 src/dom.ts >/dev/null 2>&1 &&
  { echo "  ✗ dom.ts compiled without the DOM lib; the web base is not what makes it work"; exit 1; }

echo "  ✓ base, node and web resolve by specifier; strictness and the DOM lib are real"
```

`checks/30-prettier.sh`:

```bash
#!/usr/bin/env bash
# The config is discovered from the package.json key, and it enforces the house style.
set -euo pipefail

cd tests/fixture
npm install --silent --no-audit --no-fund

# 1. Prettier finds the shared config through the "prettier" key. If it silently fell back to
#    its own defaults this would still "work", so the assertions below are what give it meaning.
npx prettier --check src/unformatted.ts >/dev/null 2>&1 &&
  { echo "  ✗ unformatted.ts passed --check; the config is not being applied"; exit 1; }

formatted="$(npx prettier src/unformatted.ts)"

grep -q "'double quotes'" <<< "$formatted" ||
  { echo "  ✗ singleQuote is not in effect"; exit 1; }
grep -q "^export const greeting = 'double quotes'$" <<< "$formatted" ||
  { echo "  ✗ semi: false is not in effect"; exit 1; }
# printWidth 100 keeps that array on one line; the default 80 would break it across lines.
[ "$(grep -c 'columns' <<< "$formatted")" = 1 ] ||
  { echo "  ✗ printWidth is not 100"; exit 1; }

cd ../..

# 2. The ignore files ship and carry the entries every project needs. They are copied rather
#    than referenced, so this proves availability, not application.
for entry in 'node_modules/' 'dist/' '.env' '.DS_Store'; do
  grep -qx -- "$entry" ignore/gitignore ||
    { echo "  ✗ ignore/gitignore is missing $entry"; exit 1; }
done
for entry in 'node_modules' 'dist' 'test-results' 'playwright-report'; do
  grep -qx -- "$entry" ignore/prettierignore ||
    { echo "  ✗ ignore/prettierignore is missing $entry"; exit 1; }
done

echo "  ✓ prettier config resolves and applies; ignore files ship with the common core"
```

### Task 4: The rules

The heart of the kit, and the task with the most judgement in it. These are **extracted** from
two existing documents, not copied: the older project's `docs/conventions.md` is titled "Engine-wide
conventions" and mixes portable rules with engine domain knowledge. Spec §5 draws the line;
this task applies it.

- [ ] **Step 4: Write `rules/http.md`**

From the older project's `docs/conventions.md` §"API conventions". Its own error table and its
scope model are that project's domain vocabulary and **stay there**. What travels is the shape
and the translation discipline.

```markdown
# HTTP

Every error response has the same shape, whatever produced it:

    { "error": "validation_error", "message": "…", "details": {} }

`details` is optional. `error` is the vocabulary the interface reads; `message` is for the log
and the test suite, and is never shown to a user.

| Code                | Status | Meaning                                          |
| ------------------- | ------ | ------------------------------------------------ |
| `validation_error`  | 400    | Body, query or path failed validation            |
| `bad_request`       | 4xx    | A framework 4xx with no better code              |
| `unauthorized`      | 401    | Missing, malformed, unknown or revoked credential |
| `forbidden_origin`  | 403    | A write whose `Origin` is not the app's own      |
| `not_found`         | 404    | No such record, or no such route                 |
| `conflict`          | 409    | The request lost a race it can retry             |
| `payload_too_large` | 413    | Body beyond the configured limit                 |
| `internal_error`    | 500    | Anything unexpected                              |

**Every request body is a TypeBox schema with `additionalProperties: false`.** Unknown fields
are rejected, never ignored: a field the server silently drops is a feature the client believes
it has.

**Framework-level 4xx are translated into this shape too.** A caller's mistake must never
surface as `internal_error`.

**Every authentication failure answers identically,** whatever actually went wrong.
Distinguishing "no such key" from "wrong secret" turns enumeration into a usable probe.

**Unexpected exceptions are logged with their stack and returned bare.** Database structure
never reaches a client through error text.
```

```markdown
# Commits

[Conventional Commits](https://www.conventionalcommits.org/): `type(scope): subject`.

| Type       | Use for                                                             |
| ---------- | ------------------------------------------------------------------- |
| `feat`     | New functionality a user can see or an API consumer can call        |
| `fix`      | Bug fix                                                             |
| `docs`     | Documentation only                                                  |
| `test`     | Adding or reworking tests without touching production code          |
| `refactor` | Neither adds behaviour nor fixes a bug                              |
| `perf`     | Performance improvement                                             |
| `build`    | Build system and dependencies                                       |
| `ci`       | CI/CD configuration                                                 |
| `chore`    | Maintenance that fits nothing else                                  |
| `revert`   | Reverting a previous commit                                         |

Pick the type by the *intent* of the change, not the file extension. A test added as part of a
new endpoint belongs to that endpoint's `feat` commit; `test` is for commits whose whole point
is coverage. Scope is optional and lowercase; omit it when the change is repository-wide.

Subject: imperative mood, lowercase first letter, no trailing period, 72 characters or fewer.
Describe the change, not the file you edited.

**The subject line is the whole message. No body, no footers, no `Co-Authored-By` trailer** —
including on commits written by an agent. A change that seems to need a paragraph is a change
that wants splitting, and reasoning that outlives the commit belongs in `docs/architecture.md`
or a spec, where someone will find it.

Each commit leaves the repository compiling and tells one story. Move bottom-up through the
dependency graph — schema, then service, then HTTP — so no commit references a module that does
not exist yet. Keep a module's tests in the commit that adds the module. Keep unrelated changes
apart: a dependency bump and a bug fix are two commits.
```

- [ ] **Step 3: Write `sh/lib.sh`**

```bash
# Sourced by a project's ./run, never executed:
#
#   source node_modules/dev-kit/sh/lib.sh
#
# Sourcing is inert. No shell options are set, no directory is changed and nothing runs — the
# caller owns `set -euo pipefail` and its own `cd`, and a library that took either would
# surprise whoever sources it halfway down a script.

# ── output ───────────────────────────────────────────────────────────────────

if [ -t 1 ]; then
  BOLD=$'\033[1m'; DIM=$'\033[2m'; RED=$'\033[31m'; GREEN=$'\033[32m'; YELLOW=$'\033[33m'; OFF=$'\033[0m'
else
  BOLD=''; DIM=''; RED=''; GREEN=''; YELLOW=''; OFF=''
fi

step() { printf '%s→ %s%s\n' "$BOLD" "$1" "$OFF"; }
ok()   { printf '%s✓ %s%s\n' "$GREEN" "$1" "$OFF"; }
note() { printf '%s  %s%s\n' "$DIM" "$1" "$OFF"; }

# Fail with an instruction, not just a symptom. The second argument is what to do about it.
die() {
  printf '%s✗ %s%s\n' "$RED" "$1" "$OFF" >&2
  [ $# -gt 1 ] && printf '%s  %s%s\n' "$YELLOW" "$2" "$OFF" >&2
  exit 1
}

# ── environment ──────────────────────────────────────────────────────────────

# `.env` is the local counterpart of what compose already substitutes for the Docker stack.
#
# Read line by line rather than sourced, so the conventional precedence holds: command line,
# then the file, then the script's own defaults. `. ./.env` assigns unconditionally and would
# let the file override an explicit `PORT=4100 ./run dev`.
#
# The grammar is plain `KEY=value`, matching what compose itself reads: no quoting, no
# expansion, `#` starts a comment. A value may contain `=`; only the first one splits.
load_env_file() {
  [ -f .env ] || return 0
  local line key
  while IFS= read -r line || [ -n "$line" ]; do
    case "$line" in '' | \#*) continue ;; esac
    key=${line%%=*}
    [ -n "${!key:-}" ] && continue
    export "$key=${line#*=}"
  done < .env
}

# ── preflight ────────────────────────────────────────────────────────────────

need_docker() {
  command -v docker >/dev/null 2>&1 ||
    die "Docker is not installed." "Install Docker Desktop, then run this again."
  docker info >/dev/null 2>&1 ||
    die "Docker is installed but not running." "Start Docker Desktop and wait for it to report ready."
}

# The floor is a variable because it is the one thing that differs between projects today, and
# a project that needs a newer Node should say so rather than fork this function.
need_node() {
  local min="${DEVKIT_NODE_MIN:-24}"
  local hint="${DEVKIT_NODE_HINT:-Install Node ${min} or newer.}"
  command -v node >/dev/null 2>&1 || die "Node is not installed." "$hint"
  local major
  major="$(node -p 'process.versions.node.split(".")[0]')"
  if [ "$major" -lt "$min" ]; then
    printf '%s! Node %s is older than the required %s.%s\n' "$YELLOW" "$(node -v)" "$min" "$OFF" >&2
    note "nvm use   (or install Node ${min}) — continuing anyway"
  fi
}

need_deps() {
  [ -d node_modules ] || { step "Installing dependencies"; npm install; }
}

# Copies the template and says so. Whatever else the project wants to tell the reader about the
# new file — which port it points at, which secret is still blank — is the caller's to `note`,
# because only the caller knows.
need_env() {
  if [ ! -f .env ]; then
    step "Creating .env from .env.example"
    cp .env.example .env
    return 1
  fi
  return 0
}
```

`need_env` returns 1 when it created the file and 0 when one already existed, so a caller can
print its own notes only on the first run:

```bash
need_env || {
  note "DATABASE_URL already points at the compose database on port ${DB_HOST_PORT}"
  note "ENGINE_API_KEY is empty — see the README for how to issue one"
}
```

Under `set -e` that idiom is safe: a non-zero status on the left of `||` is handled, not fatal.

- [ ] **Step 5: Commit and tag**

```bash
./check
git add -A
git commit -m "docs: describe the consumption contract"
git tag -a v1.0.0 -m "v1.0.0"
git tag -l
```

**An immutable version tag, not a moving `v1`.** Spec §6 writes the pin as `#v1` as shorthand.
Use `v1.0.0`: npm caches git dependencies by ref, and a tag that moves is a tag that does not
reliably refetch, which would turn "pin a version" into "sometimes get the old one". A
consuming project pins `#v1.0.0` and bumps deliberately, which is what §6 actually argues for.

**Publishing is deferred, and the tag is what makes deferring safe.** No private registry
exists on this machine yet, so v1.0.0 ships on the git channel alone. Spec §6 requires only
that a release which *is* published is tagged from the same commit, and this tag satisfies
that in advance: when a registry appears, `npm publish` from the `v1.0.0` tag produces the
identical tree.

**When that day comes, pass the registry explicitly** — `npm publish --registry <url>`, or a
`publishConfig.registry` in `package.json`. A bare `npm publish` targets the public registry,
which spec §1 forbids. It would in fact fail with a 403, because the name belongs to someone
else there, but relying on a stranger's ownership as an access control is not a safeguard.

- [ ] **Step 6: Verify a real consumer can install it**

The last thing this plan claims is that a project on any machine can take a dependency on
this. Prove it rather than assert it:

```bash
cd "$(mktemp -d)"
npm init -y >/dev/null
npm install "github:AlexeyVanyukevich/dev-kit#v1.0.0"
node -e "console.log(require('dev-kit/package.json').version)"
ls node_modules/dev-kit
```

Expected: `1.0.0`, and a directory listing showing `rules`, `tsconfig`, `prettier`, `sh` and
`ignore` — and **not** `checks`, `tests` or `docs`, which `files` excludes.

This step needs the repository pushed to a remote. **Done on 2026-09-24:** the remote is
`github:AlexeyVanyukevich/dev-kit`, and it is **public**.

Private was recommended here first, on the grounds that spec §1 keeps the kit off the public
registry and a public repository would put the same content in the open by the other door.
That was weighed and declined, and the reason it is safe to decline is worth recording,
because it is a property of spec §5's extraction rather than a matter of luck: **nothing
project-specific reached the package.** A search of `rules/` for the domain vocabulary of
either consuming project returns nothing, and the only matches for secret-shaped words are
two sentences discussing secrets in the abstract. What is public is a set of generic
TypeScript, HTTP and testing conventions and a shell library.

Spec §1 is untouched by this. It forbids the public **npm registry**, and a public git
repository publishes nothing there — the name-collision reasoning in spec §4 stands exactly
as written.

The one thing this forecloses: a rule carrying something a consuming project would not want
read can no longer simply be added. Extraction discipline was a design preference on
2026-09-08; from 2026-09-24 it is the only thing standing between the two built projects and
the open internet.

**The registry channel is not verified here, and that is the one loose end this plan ships
with.** No private registry exists yet, so the `"dev-kit": "^1.0.0"` row of the README is
documented but unproven. When a registry is stood up, prove it once with the same shape as
above — publish to it, then in a scratch directory write `registry=<url>` into `.npmrc`,
`npm install dev-kit@^1.0.0`, and check `require('dev-kit/package.json').version` reads
`1.0.0` and that `node_modules/dev-kit/rules` exists. The failure worth watching for is the
install silently succeeding with the **unrelated public `dev-kit`**, which is what an `.npmrc`
that did not take looks like: its version will not be `1.0.0` and it has no `rules/`
directory. Both assertions above catch it; the version check alone is what makes the check
meaningful rather than decorative.
